# Infinity Agents — 工作区、图像示例与统一交互改造执行文档

> 状态：实施中；Cloudflare 基线已发布并通过只读 smoke。本轮统一工作区 UI 已完成本地质量检查，但真实 Worker/Case 2–3 闸门尚未通过，因此不把本轮改动提前宣称为已发布。
> 日期：2026-08-10
> 适用分支：`cloudflare-deploy`；本地 `main` 的现有修改不在本轮规划中被覆盖。

旧执行文档只作为本文件的参考来源，保持原样；本文件是当前这组前端改造、后续测试和发布闸门的统一入口。

## 0. 本轮边界

本轮按本文件执行，界面、账户设置、持久 Worker、本地真实链路、三方验收和 Cloudflare 发布均已完成；以下事项明确不在本轮：

- Redis、PostgreSQL 或 Cloudflare 线上数据的清理；
- 把图像示例误认为已经完成的通用性状提取能力。

现有 Cloudflare 分支已经具备一版直接创建任务和持久 Worker 注册的实现；本文件把它作为基线，后续以小步修改方式对齐新的工作区和移动端结构。

## 1. 总目标

把 Infinity Agents 从“多个页面各自放表单”收敛成一个统一工作区：

```text
登录一次
  → 在同一个 Infinity Agents 工作区中切换 Analysis、任务执行中心、性状提取
  → 左侧显示当前工作区的上下文列表
  → 右侧显示当前选中内容
  → 任务和 Worker 都由数据库保存并可恢复
  → 手机端通过抽屉使用同一套工作区
```

最终目标不是增加更多入口，而是让用户清楚知道：

1. Analysis 负责对话、研究和提出执行意图；
2. 任务执行中心负责直接创建、查看和跟踪异步任务；
3. 性状提取负责查看图像分析示例并逐步承接真实的结构化表型数据能力；
4. Worker 是用户集群中的持久执行节点，不是一次性临时凭证；
5. PostgreSQL/D1 保存事实，Redis 负责通知和唤醒，浏览器不直接拥有数据库或 Redis 权限。

## 2. 已冻结的产品决定

### 2.1 任务执行中心

桌面端任务执行中心采用“左工作区、右主内容”的布局：

| 区域 | 内容 |
|---|---|
| 左侧 AgentNav 下方 | “新建任务”按钮、当前用户的任务列表；没有任务时显示“暂时无任务” |
| 右侧第一块 | “创建任务”卡片，直接创建异步任务 |
| 右侧第二块 | “添加 Workers”卡片，默认折叠 |
| 任务点击 | 打开任务详情，查看状态、Attempt、Worker 和结果 |
| 左下角 | 当前用户名称在左，退出登录按钮在右 |

任务执行中心里的“创建任务”是用户主动操作，不再等待 Analysis 再确认一次；它仍然复用 TaskSpec、Method、Dataset、幂等和任务 API，通过服务端专用的 `/api/tasks/direct` 路由提交，并明确传递 `agent_confirmation=false`/`chat_confirmation_id=false`。通用 `/api/tasks` 路由不接受调用方伪造的 Task Center 来源字段。

Analysis 对话中的确认卡仍保留原有语义：由 Analysis 提议，用户确认后再提交。两条入口最终进入同一个任务状态机，不能各自维护一套任务创建逻辑。

### 2.2 任务名称与数据处理边界

任务名称的默认值取执行文档名称，因为执行文档是区分任务意图和执行方法的主要信息；数据内容的不同不应自动替换任务名称。用户仍可以在提交前修改名称。

本轮不新增以下功能，也不改变现有数据流程：

- 不建立公共数据资源库；
- 不新增跨任务数据引用、数据复用或上传去重；
- 不要求同一份数据只能上传/打包一次；
- 不把“联合分析”扩展成新的前端数据管理功能。

每个任务继续按当前任务创建流程选择、上传和打包自己的数据。后续如果确实需要数据复用，应另开产品设计和后端数据契约，不在本轮前端改造中顺带实现。

### 2.3 左下角用户区与“新建任务”

任务执行中心和 Analysis 一样，在 AgentNav 下方提供一个明确的“新建任务”按钮。它首先创建一个本地任务草稿并清空上一份表单；只有用户点击创建后才调用任务 API，不因点击按钮就产生空任务。

- 如果当前草稿已经填写内容，切换前提示用户确认丢弃；
- 新任务表单默认把执行文档文件名/文档名称填入任务名称；
- 用户手动修改名称后，重新选择数据不应覆盖用户输入；
- 创建成功后任务出现在左侧列表，右侧表单回到下一份新草稿；
- 左下角固定显示当前用户名称，右侧显示“退出登录”；名称缺失时按邮箱显示；
- 退出登录调用同源 Auth logout，清理前端状态并回到登录入口；
- 手机端工作区抽屉底部复用同一用户区，不复制另一套账户逻辑。

### 2.4 文件分析示例

ImageJudge 页面沿用 Analysis 的工作区结构：左侧原来显示对话的区域改为可点击的 ImageJudge 示例选项卡；点击某个示例后，右侧打开对应的运行实例：

1. 顶部横向展示参考图片；
2. 下方展示已上传/待分析图片；
3. 每张待判断图片下面展示对应的判断结果，再补充图片说明、分析规则、判定类别和待人工复核信息；
4. 示例先使用版本化的本地/仓库 Fixture，不把示例原图自动上传到 Web；
5. 现有参考图分类结果只能称为兼容模式，不能宣传为已经支持所有物理性状测量。

第一版先把“示例浏览和结果解释”做好，数据模型预留 `TraitDefinition`、`TraitObservation`、标定信息和 QC，不在本轮擅自开放没有标定依据的株高、长度、面积等绝对数值。

### 2.5 机器人头像和无闪烁交互

- Analysis 页面移除“导出 PDF”入口和对应的前端导出功能；桌面端和手机端都不保留；
- Analysis、任务执行中心和性状提取页面移除旧的右上角“下载最新版本”入口；导出 PDF 也从工作区移除；需要下载应用时从统一左侧导航进入独立的“下载最新应用程序”页面；
- 原有桌面分发文档和安装包能力暂不删除，只是不再从主工作区暴露入口；
- 对话中的 Assistant 头像统一使用现有产品 Logo 资源，优先复用 `frontend/app/icon.png`，不临时使用字母或随机图标；
- 首屏、路由切换、任务轮询、图片加载和语言初始化不能造成整页闪烁；
- 刷新任务列表时保留旧内容，只更新状态，不把整个区域先清空；
- 加载状态使用尺寸稳定的 skeleton/占位，不让页面高度来回跳动；
- 图片区域固定宽高或使用稳定的 aspect ratio，避免图片加载后布局重排；
- 交互动画只用于 opacity/transform 等稳定属性，并遵守 `prefers-reduced-motion`；
- 错误边界和加载边界不能把已显示的工作区替换成短暂空白页面。

### 2.6 手机端

手机端保留一个 Analysis 主对话体验，不再复制桌面端的多栏 Agent 布局。左上角提供菜单按钮，打开一个类似 ChatGPT 的工作区抽屉：

- 抽屉中显示桌面端同一套工作区入口和当前工作区的上下文列表；
- Analysis 显示对话列表，任务执行中心显示任务列表，性状提取显示示例列表；
- 点击入口后关闭抽屉并保留当前页面状态；
- 支持遮罩点击、返回键/Escape、焦点回收和滚动锁定；
- 导出 PDF 已从整个产品工作区移除，手机端不需要单独处理这个入口；
- 中英文切换按钮从桌面和手机两端都移除，语言由系统/浏览器语言和 Infinity Agents 用户设置决定。

手机端的“只有 Analysis Agent”表示只有一个主对话 Agent；任务和性状提取是工作区，不再另造独立的聊天人格。

### 2.7 语言设置

语言设置属于 Infinity Agents 自己的用户设置，不放进 Auth 用户资料：

- Auth 只负责身份、登录和会话；
- Infinity Agents 数据库新增/使用 `user_settings`（或等价表），至少保存 `locale`；
- 第一次创建用户设置时读取浏览器/操作系统语言，写入 Infinity Agents；
- 服务端已有设置时优先使用已保存值，避免每次登录因为设备语言变化而闪烁；
- 首屏尽量在服务端/布局层拿到语言，再渲染页面；
- 暂不提供页面内语言切换按钮，后续若需要改语言再做用户设置页。

### 2.8 Worker、账户和 Namespace

Worker 是当前登录用户集群中的机器身份，绑定关系必须由服务端数据库保存和检查：

- 用户只填写 Namespace；Worker ID 由服务端生成；
- 同一用户可以在同一 Namespace 下拥有多个不同 Worker ID；
- Namespace 可以复用，但 `(user_id, worker_id, namespace)` 不能越权复用；
- 只有超级用户映射为完全信任；普通用户和学生都按一般信任处理；
- Worker 注册记录、状态、信任等级、最后心跳和凭证摘要保存到数据库；
- 正常 UI 流程只创建 `worker_registrations` 中的非过期持久凭证，不创建一次性 enrollment token；旧 `worker_enrollments`/`enrollment_token` 仅作为历史客户端兼容路径，不是本轮注册入口；
- “注册状态”和“在线状态”分开：`active` 表示仍属于集群且凭证有效，`online/offline` 由 `last_seen_at` 和心跳窗口推导；
- Worker 停止后不自动注销、不删除、不生成新 ID，只显示“已注册 · 离线”；重新启动原配置后恢复为在线；
- 在线窗口使用可配置的心跳超时（当前心跳间隔 30 秒，可先按约 90 秒判断在线），不需要为离线状态增加数据库枚举；
- 凭证不依赖 Cookie 或 Local Storage 作为权限判断，浏览器只保存 UI 状态；
- 持久 Worker 凭证只在注册/轮换响应中交给用户，服务端在数据库保存其摘要（可长期校验、可单独撤销），客户端 Worker 将原始凭证保存为本机受限配置；数据库不保存可直接还原的明文 secret；
- 每次 Control API 请求都校验 Worker 凭证、Namespace、所属用户、状态和任务授权，不能只相信前端传入的 Namespace；
- 任务分配只面向最近在线且未 revoked/draining 的 Worker；Worker 突然掉线时由现有 lease/fencing 机制恢复任务，不把掉线误报为注销；
- Worker 可以在自己的机器上创建 Docker Job，但不能因此获得其他用户的 Worker、Task、数据库或 Redis 权限；
- 撤销、draining、轮换和重新加入都必须有数据库状态记录。

这意味着“登录我的账户就属于我的集群”是服务端授权事实，不是把账户 ID 写进 Cookie 后由前端推断出来。

## 3. 目标 UI 结构

| 工作区 | 左侧上下文区 | 右侧主内容 |
|---|---|---|
| Analysis | 新建对话、最近对话、运行活动 | 对话、消息、Composer |
| 任务执行中心 | 新建任务、当前用户任务；空列表显示“暂时无任务” | 创建任务、添加 Workers（默认折叠） |

## 4. 目标驱动执行顺序

每个阶段只交付一个可观察结果，完成后再进入下一阶段。G0–G8 已完成，线上只读 smoke 已记录。

### G0 — 冻结工作区合同

**结果：** 形成统一的页面/状态/入口合同，不改业务代码。

- 确认三个工作区名称和 URL 是否继续保留 `/`、`/code-agent`、`/image-judge`；
- 确认桌面侧栏的宽度、任务行字段和空状态文案；
- 确认左下角用户名称、退出登录按钮和“新建任务”按钮的位置；
- 确认任务默认名称取执行文档名称，且不把数据名称作为默认任务名称；
- 确认移除导出 PDF 和性状提取下载最新版本入口；
- 确认示例使用仓库 Fixture 还是用户上传数据；
- 确认 Logo 资源和语言设置字段；
- 建立一份字段表，后续各页面只使用同一份任务、示例、用户设置、Worker 类型。

### G1 — 重排任务执行中心

**结果：** 桌面任务中心左侧显示“新建任务”和任务列表，右侧只显示创建任务和折叠 Worker 卡。

主要范围：

- `frontend/app/code-agent/page.tsx`；
- 任务列表的紧凑状态行、空状态和详情跳转；
- 左侧“新建任务”按钮、草稿重置和未保存内容提示；
- 复用当前 `TaskCreationCard`、`WorkerEnrollmentPanel`，不再复制任务创建函数；
- 任务名称默认从执行文档名称生成，保留用户手动修改；
- 保持当前每个任务自己的数据上传/打包流程，不增加数据引用或公共数据管理；
- 保留轮询但避免刷新时清空内容。

门槛：只做静态/交互实现，先由用户确认布局，再进入自动化测试。

### G2 — 建立性状提取示例浏览器

**结果：** 左侧可以点选示例，右侧能稳定展示参考图片、上传图片和判定信息。

主要范围：

- 示例选择状态、空状态、加载状态、错误状态；
- 参考图横向区域和上传图区域；
- 说明、类别、结果和待复核字段；
- 与现有 ImageJudge 分类兼容模式对齐，不伪造新的模型结果。

### G3 — 统一 Logo 和稳定交互

**结果：** 对话头像统一为产品 Logo，常见操作不再整页闪烁。

主要范围：

- `MessagePane`/Avatar 统一渲染入口；
- 稳定的 loading/skeleton 和图片占位；
- 任务刷新、导航、错误重试和提交状态的局部更新；
- 移除造成布局跳动的临时空节点或不稳定高度；
- 加入减少动画偏好的样式约束。

### G4 — 手机工作区抽屉

**结果：** 手机端左上角菜单可以打开/关闭工作区和当前列表，Analysis 对话不被破坏。

主要范围：

- 共享 `WorkspaceShell`/`MobileWorkspaceDrawer`；
- 菜单按钮、遮罩、Escape/返回键、焦点和滚动行为；
- 任务中心和性状提取沿用各自的上下文列表；
- 移除移动端导出 PDF；
- 保持桌面端侧栏和手机抽屉使用同一数据源。

### G5 — Infinity Agents 用户设置与系统语言

**结果：** 用户创建后有 Infinity Agents 设置记录，页面不再显示中英文切换按钮且首屏语言稳定。

主要范围：

- `user_settings` migration、owner 约束和查询 API；
- 首次登录创建设置时同步系统语言；
- SSR/布局层读取设置，前端只做无闪烁 fallback；
- Auth 只保留身份职责，不把产品设置写进 Auth。

### G6 — 持久 Worker 与集群边界对齐

**结果：** 已有 Worker 注册实现与新的 UI、用户设置和授权模型一致。

主要范围：

- 审核 `worker_registrations` 与旧 `worker_enrollments` 兼容边界；
- 校验同 Namespace 多 Worker、超级用户/普通用户信任等级和撤销逻辑；
- 增加“已注册/在线/离线/从未连接”的派生显示，停止 Worker 后不改变注册记录；
- 在 Mac 上用两个不同 Worker ID 和凭证加入同一用户 Namespace，停止两个进程后确认记录仍在、状态变为离线；重新启动后确认恢复在线；
- 确认客户端配置、凭证轮换和“查看我的 Workers”行为；
- 确认本地 PostgreSQL/Redis 和 Cloudflare D1 的事实边界；
- 不让浏览器或学生 Worker 直连 Redis、D1/PostgreSQL、R2 parent credential 或 Cloudflare API。

### G7 — 集成验收（基线已完成，本轮改动待复核）

**结果：** 上一版基线已经通过自动化检查、真实本地链路、两个浏览器 Subagent 和 Zeal Review；本轮新增统一侧栏、任务详情保留列表和独立下载页后，必须重新完成对应的浏览器/Review 闸门。

实际执行顺序：

1. 先做类型检查、单元测试和构建；
2. 再做本地真实 API/数据库/Redis 流程；
3. 再让两个浏览器 Subagent 分别操作桌面和手机关键路径；
4. 另一个 Review Agent 做代码审查；
5. 有问题先修复，再重复对应门槛；
6. 首轮发现本地 Worker GET/POST 兼容、回环来源和权限投影问题；修复后桌面端、手机端和 Review 均重新通过。

## 5. 每个阶段的执行卡格式

后续开始执行时，每次只打开一张卡：

```markdown
# EXEC-Gx: 一个可观察结果

## 当前基线
- 分支 / commit
- 已有 dirty files
- 依赖的现有实现
```

## 6. 现在需要先讨论的最小决定

我建议按下面默认值开始：

1. **图像示例来源：** 第一版使用仓库内版本化 Fixture；用户上传和真实批量分析放在后续数据链路，不让 UI 先依赖不存在的后端接口。
2. **任务名称：** 默认取执行文档名称；数据仍按当前任务流程上传/打包，不新增数据引用复用功能。
3. **Logo：** 复用 `frontend/app/icon.png`；如果它不是最终产品 Logo，再替换一个统一资源入口，页面不直接写死文件名。
4. **语言优先级：** 已保存的 Infinity Agents `user_settings.locale` 优先；没有设置时读取系统语言并创建设置；不再显示切换按钮。
5. **手机抽屉：** 顶层只有 Analysis 对话体验，抽屉里提供任务中心和性状提取工作区，不增加第二个聊天 Agent。
6. **Worker 凭证：** 数据库保存摘要和状态，客户端本机保存可用凭证；丢失时走轮换，不把原始凭证写进浏览器 Cookie/Local Storage 或日志。
7. **执行顺序：** 先 G1 让任务中心布局稳定，再 G2/G3/G4，最后处理 G5/G6 的数据和授权细节；G7 之前不做真实验收，G8 最后做。

## 7. 统一测试、验收与发布流程

本节把旧执行文档中的“单一模型执行循环、本地测试分层、真实浏览器验收、负向测试、证据包和远程发布闸门”收敛到当前任务。旧文档不改；后续执行只按本节和本文件当前产品决定操作。

### 7.1 统一执行循环

每一张执行卡只允许一个可观察结果，不把布局、认证、数据库、Worker 和部署混成一张卡：

```text
读取本文件和最新 checkpoint
→ 只读检查 dirty worktree、当前分支和基线
→ 运行该卡的 baseline
→ 做最小改动
→ 运行正例、负例和必要的集成检查
→ 检查 diff、Secret、页面入口和回滚点
→ 保存 checkpoint 与证据
→ 通过当前 Gate 后再进入下一张卡
```

每张卡必须记录：

- 当前 commit、dirty 文件和允许修改范围；
- 目标、明确的非目标、风险和回滚方式；
- 实际执行的命令、退出码、通过/失败/跳过原因；
- 浏览器、API、数据库、Redis、Worker 状态；
- 截图、trace、日志和脱敏后的证据路径；
- 未解决问题和下一张精确执行卡。

“代码看起来完成”或“模型说通过”都不算验收通过。

### 7.3 自动化检查顺序

### 7.4 G1–G6 的具体验收用例

#### F2：任务执行中心

1. 打开任务中心，左侧 AgentNav 下出现“新建任务”和任务列表；
2. 无任务时显示“暂时无任务”，不显示空表格残影；
3. 点击“新建任务”只创建本地草稿，不产生服务端任务；
4. 选择执行文档后，任务名称默认等于执行文档名称；
5. 选择数据不会覆盖用户手动修改过的任务名称；
6. 未保存草稿切换前能看到丢弃提示；
7. 提交后只创建一个任务，任务立刻出现在左侧；
8. 任务中心直提交不需要 Analysis 再确认，但仍走同一 TaskSpec/幂等/状态机接口；
9. 右侧 Worker 卡默认折叠，展开后只要求 Namespace；
10. 左下角名称在左、退出登录在右，logout 后当前会话和受保护 API 都失效。

#### F3：文件分析示例

1. 左侧示例可以逐项点击，并明确显示当前项；
2. 右侧顶部是横向参考图片；
3. 参考图片下方是上传图片/分析图片区域；
4. 说明、类别、结果和人工复核信息在同一个示例上下文中；
5. 示例加载、空列表、坏图片和结果缺失都有稳定状态；
6. ImageJudge 页面不再出现旧的“下载最新版本”入口；统一左侧“下载最新应用程序”进入独立 `/downloads/` 页面，不把示例页当作下载页。

#### F4：稳定交互和统一入口

1. Analysis Assistant 使用产品 Logo；
2. 任务轮询不会先清空原列表；
3. 路由切换、图片加载和错误重试不会造成整页白屏或明显跳动；
4. 无 Export PDF 入口；
5. 失败重试保留用户已输入的草稿和已显示的旧结果；
6. `prefers-reduced-motion` 下不强制播放非必要动画。

#### F5/F6：手机和用户设置

1. 手机左上角菜单可以打开工作区抽屉；
2. 抽屉显示当前工作区列表和对应上下文列表；
3. 选择入口、遮罩、返回键/Escape 后抽屉正确关闭；
4. 抽屉底部显示用户名称和退出登录；
5. 手机和桌面都不显示 Export PDF 和语言切换按钮；
6. 系统语言第一次进入时写入 Infinity Agents 设置，后续加载不因语言初始化闪烁。

#### F7：Worker 前端合同

1. 普通用户和学生显示一般信任，超级用户显示完全信任；
2. 同一 Namespace 可生成多个不同 Worker ID；
3. 刷新页面后已注册 Worker 仍显示；
4. Worker 的注册状态来自数据库，在线状态由最近心跳推导，不来自浏览器猜测；
5. 停止本地两个 Worker 后记录仍存在，但显示为离线；重新启动原配置后恢复在线；
6. 另一用户不能看到、撤销或使用当前用户的 Worker；
7. 原始凭证不进入 URL、日志、普通 Local Storage 或页面初始 HTML。

### 7.5 负向、安全和恢复验收

以下用例必须作为失败路径明确记录，不能只测正常点击：

- 未登录访问任务、Worker、用户设置 API 必须被拦截或跳转登录；
- logout 后旧页面不能继续读写受保护资源；
- Alice/Bob 不能通过任务 ID、Worker ID、Namespace、事件流或详情 URL 互相读取；
- 重复点击、网络超时重试和重复 idempotency key 不能创建两个任务；
- API 失败时保留已有 UI 状态，不显示假成功；
- Worker 注册失败时不把半成品 Worker 写入列表；
- 刷新、关闭抽屉和返回页面不泄露 Worker 原始凭证；
- 浏览器、日志、截图和构建产物不得出现 Auth、数据库、Redis、Provider 或 Worker Secret；
- 旧 Redis/数据库服务不被测试脚本清空，验收必须使用独立 namespace。

### 7.6 两个浏览器 Subagent 与一个 Review Agent

只有 G1–G6 的自动化检查通过后才启动真实验收：

1. 浏览器 Subagent A：桌面端，逐项操作 Analysis、任务中心、性状提取、用户栏、logout；
2. 浏览器 Subagent B：手机尺寸，操作菜单抽屉、任务草稿、图像示例和返回流程；
3. Review Agent：检查组件边界、认证/权限、状态竞态、无障碍、重复逻辑和 Secret 泄漏。

每个 Agent 都要提交“通过/失败 + 复现步骤 + 截图/trace + 严重等级”。发现问题后先修复，再让 Review Agent 对修复范围复核；没有通过三方报告不能进入 Cloudflare。

### 7.7 证据包与停止条件

每一轮验收保存脱敏证据，例如：

```text
current-acceptance/<run_id>/
├── manifest.json
├── versions-redacted.txt
├── screenshots/
├── browser-traces/
├── test-results/
├── api-logs-redacted/
├── worker-logs-redacted/
└── checksums.sha256
```

遇到以下情况必须停在当前卡并报告，不得自行扩大范围：产品决定缺失、出现跨用户访问、任务重复、凭证泄漏、数据库/Redis 需要破坏性清理、Cloudflare 需要新权限、测试失败原因不明。

### 7.8 发布闸门

```text
G1–G6 实现完成
→ F1–F7 自动化/集成检查通过
```
